# Event Storming 協作建模工具教學內容設計框架與原則

本框架旨在針對「Event Storming (事件風暴)」協作建模工具，提供一套結構化、實戰導向的教學內容設計原則。在編寫 Event Storming 教材時，應遵循以下 8 大核心結構元素與設計原則，引導學員從認知建立、語意掌握、流程實作，最終走向軟體設計與敏捷交付。

---

## 1. 原則 1：價值錨定與痛點對比 (Why & What)
教學內容的第一步必須建立學員對 Event Storming 的「心智模型」，解決「為什麼要使用此工具」的根本問題。
* **痛點揭示**：對比傳統需求分析方式（如：長篇幅純文字規格書、難以理解的靜態 UML 類別圖/流程圖、跨部門溝通斷層）。指出這些方式如何導致**語意歧義**、**漏失極端情境 (Corner Cases)**、以及開發團隊與業務部門之間的「穀倉效應」。
* **工具核心價值**：明確指出 Event Storming 如何透過「時間軸 (Timeline)」與「統一語言 (Ubiquitous Language)」，讓業務專家與技術人員在同一個視覺化白板上協作，快速拉齊理解並暴露流程瓶頸與爭議點（Hot Spots）。

## 2. 原則 2：解剖結構與語意定義 (Structural Anatomy & Notation)
拆解 Event Storming 看板的物理與邏輯元素，讓學員理解各類彩色貼紙的定義與相互關係。
* **維度與方向定義**：
  * **時間維度**：看板由左至右代表時間軸（Timeline）的演進。
  * **觸發與響應維度**：
    * **主導/輸入**：`Command (命令)`、`Policy (反應式規則/政策)` 或 `Actor (執行角色)`。
    * **響應/輸出**：`Domain Event (領域事件)` 與 `Read Model (讀取模型/資訊檢視)`。
* **貼紙標記語意**：
  * **橘色貼紙 (Domain Event)**：領域事件，代表業務中已發生且重要的事實（使用過去式動詞，如：`訂單已建立`、`款項已支付`）。
  * **藍色貼紙 (Command)**：命令/意圖，代表使用者或系統的操作（如：`提交報銷單`）。
  * **黃色貼紙 (Aggregate)**：聚合/業務實體，處理命令並確保業務規則的決策邊界。
  * **紫色貼紙 (Policy/Rule)**：反應式規則，當事件發生時自動觸發下一個命令（「當...時，就...」）。
  * **綠色貼紙 (Read Model)**：讀取模型，使用者做決策或下命令時參考的資訊（如：`剩餘額度`）。
  * **黃色小貼紙 (Actor/Role)**：執行角色，觸發命令的主體。
  * **紅色貼紙 (Hot Spot)**：熱點，代表衝突、待確認問題或技術風險。

## 3. 原則 3：標準建模作業程序 (Modeling SOP)
為學員提供一套從零開始的漸進式 Event Storming 建模步驟，降低面對空白畫面的焦慮。
* **第一步：識別與列舉領域事件 (Domain Events)**：腦力激盪，寫下所有業務中發生的關鍵事件（橘色貼紙）。
* **第二步：時間軸排序與去重 (Enforce Timeline & Deduplicate)**：將事件按時間由左至右對齊，拉出流程主線，找出關鍵事件 (Pivotal Events)。
* **第三步：尋找觸發源與決策實體 (Commands, Actors, Read Models, Aggregates)**：為事件配對其觸發的 Command（藍色貼紙）、執行角色（黃色小貼紙）以及所需的 Read Model（綠色貼紙），並識別負責執行業務規則的 Aggregate（黃色貼紙）。
* **第四步：配置反應式規則與熱點 (Policies & Hot Spots)**：梳理「事件 ➔ 政策/規則 (紫色) ➔ 命令」的反應鏈，並將爭議處貼上紅色 Hot Spot。

## 4. 原則 4：引導式範例拆解 (Guided Case Study)
設計一個兼具代表性與適度複雜度的業務場景，作為課堂演示的載體。
* **業務場景**：選擇源自學員日常容易理解的場景（如：**員工教育訓練補助申請與核銷** 或 **差旅費用申請與報支**），避免過於生硬的技術架構名詞。
* **解讀演示法**：教材應示範如何利用看板說故事：
  * **橫向讀路徑**：沿著時間軸解讀業務流（例如：「當員工看見可用額度後，提交了申請單...」）。
  * **縱向讀規則**：解讀特定事件如何透過 Policy 自動觸發下一個流程，以及 Aggregate 如何防守業務邊界。

## 5. 原則 5：漸進式實戰練習設計 (Progressive Practice Design)
實作練習不可一蹴可幾，應設計成三層級的漸進挑戰：
* **Level 1：閱讀與填空 (Guided Fill-in)**：給予一張完成 80% 的設計級看板，讓學員根據簡單的新需求描述（如：「當退回審核時，需通知申請人」），補上剩餘的貼紙（如 Policy 或 Command），重點在熟悉語意與元素間的連結。
* **Level 2：分析與邏輯糾錯 (Logic Debugging)**：提供一個刻意寫錯的看板（如：有 Event 但無 Aggregate、Policy 沒有輸入事件、或者時間軸逆向），讓學員找出 Bug，學習防禦性建模。
* **Level 3：情境具現化 (Scenario-to-Model)**：給予一段口語、雜亂的業務訪談稿或使用者故事，要求學員分組在牆面上（或線上白板）完全獨立完成建模。

## 6. 原則 6：工作坊引導與協作氛圍 (Workshop Facilitation & Collaboration)
Event Storming 本質上是一場「引導工作坊」，教材應包含如何引導與促進團隊協作的指南。
* **物資與空間整備**：強調無限寬度的實體牆面/線上白板，以及準備充足的彩色貼紙與馬克筆。
* **引導師的角色定位**：如何調和「業務專家 (Domain Experts)」與「技術人員 (IT/Developers)」的溝通。確保技術人員不會過早將討論拉入「資料表欄位」或「資料庫設計」，並引導業務專家說出真實痛點。
* **時間盒與焦點管理**：使用 Timeboxing 機制，對於無法現場達成共識的爭議，迅速貼上紅色 Hot Spot 掛號，確保工作坊順暢進行。

## 7. 原則 7：常見盲點與避坑指南 (Pitfalls & Best Practices)
總結歷屆學員最容易犯的思維錯誤，做成防錯檢查清單。
* **過度建模 (Over-modeling)**：警告學員不要試圖在一張看板上解決整個企業的所有細節。應學會適時使用 Bounded Context 進行邊界劃分。
* **技術細節混入**：提醒學員避免貼上「點擊按鈕」、「寫入 DB」等純技術實現貼紙，確保所有貼紙都代表業務邏輯。
* **名詞分歧**：引導學員在建模過程中收斂名詞，建立團隊間唯一的統一語言 (Ubiquitous Language)。

## 8. 原則 8：驗證與延伸思考 (Reflection & Validation)
建模的目的不是畫出好看的圖表，而是為了指導後續的開發、測試或業務決策。
* **測試案例生成**：引導學員將「Command ➔ Aggregate ➔ Event」的完整路徑，直接轉化為行為驅動開發 (BDD) 的 Given-When-Then 測試案例。
* **代碼與架構映射**：說明此看板如何對應到軟體架構（如 Domain-Driven Design 或 Event-Driven Architecture）：
  * Domain Event ➔ 訊息佇列事件 (Event Message)
  * Command ➔ API 介面/命令處理器 (Command Handler)
  * Aggregate ➔ 領域實體與聚合根 (Domain Entity & Aggregate Root)
  * Policy ➔ 事件監聽器 (Event Listener) 或工作流 Saga
